# Retrieval contract (Milestone 2)

Milestone 2 evaluates product discovery only: given the shopper's original query text and the correct exact filters,
are the right candidate SKUs retrieved? Language understanding (turning text into filters) belongs to the Milestone 3
shopper. Final purchase decisions (delivery, returns, installments, safety) are out of scope.

## Search document

There is one document per published SKU (`SearchDocumentBuilder`). Fields:

| Field | Source | Use |
|---|---|---|
| `storeVersion`, `sku`, `productId`, `category`, `title`, `brand` | published catalog | identity, display, category filter |
| `semanticText` | published catalog (see below) | embedded |
| `contentHash` | SHA-256 of `"semantic-doc-v1\n" + semanticText` | idempotent re-indexing |
| `priceTry` | published Pricing (`price-list.json`) | max-price filter |
| `availableQuantity` | published Inventory (`inventory.json`) | in-stock filter |
| `shoeSize`, `color` | published variant attributes | exact filters |
| `laptopSizeIn`, `capacityLiters`, `batteryHours`, `warrantyMonths` | published product attributes (null when missing) | minimum-threshold filters |

The authoritative Pricing and Inventory files are used, never the catalog projections, so a SKU the catalog still shows
as `IN_STOCK` with 0 units is filtered out.

## Semantic document construction

These lines are joined with `\n`, in fixed order; lines with empty values are omitted:

```
Ürün: <title>
Kategori: Sırt çantası | Spor ayakkabı | Kulaklık | Küçük elektronik
Marka: <brand>
Ürün tipi: <productType>
Açıklama: <published description>
Özellikler: <label>: <value>; ...   (product-level attributes except brand, in requirement order)
Varyant: <size> numara, <color>     (variant attributes, sneakers only)
```

- Values are rendered in Turkish:
  - water resistance becomes "su geçirmez değil" / "su itici" / "tamamen su geçirmez";
  - booleans become "var" / "yok";
  - decimals use a comma.
- **Never embedded:** price, compare-at price, stock status or quantity, delivery promise, installments, return
  eligibility. These are volatile commerce facts owned by structured or tool sources.
- Changing the template requires bumping `ContentHash.TemplateVersion`, so every document is re-embedded.

## Structured-filter policy

Principle: an exact numeric or categorical meaning goes to deterministic filtering; a fuzzy buyer meaning goes to
semantic retrieval. `RetrievalPolicy` maps the existing `ShopperConstraints`:

| Constraint | Treatment |
|---|---|
| `Category`, `MaxPriceTry`, in stock (always), `ShoeSize`, `Color` | hard filter |
| `MinimumLaptopSizeIn`, `MinimumCapacityLiters`, `MinimumBatteryHours`, `MinimumWarrantyMonths` | hard filter; a missing published value fails it |
| `MinimumWaterResistance`, `ProductType`, `TargetGroup`, `NoiseCancellation`, `Microphone` | semantic: defines relevance, carried only by the query text |
| `DeliverTo`, `DeliverWithinDays`, `InstallmentCount`, `ReturnRequirement` | excluded from retrieval relevance (later shopper tools) |

## Search modes

| Mode | Filters | Ordering |
|---|---|---|
| `StructuredOnly` | hard filters | SKU ordinal (neutral: no relevance ranking; max price is a constraint, not "cheapest first") |
| `SemanticOnly` | none (only the store version and embedding-profile partition) | cosine distance |
| `Hybrid` | hard filters | cosine distance |

Ranking rule, shared by pgvector and the in-memory reference index:

- Cosine distance is compared at 1e-6 precision (rounded half away from zero), then ties break by SKU ordinal.
- `similarityScore` = 1 - cosine distance.
- Search is exact (no HNSW/IVFFlat): the corpus is about 100 SKUs.

## Indexing

Index rows are keyed by `(store_version, embedding_model, embedding_dimensions, sku)`, so vectors of different
embedding profiles are never compared.

Re-indexing:

- embeds only documents whose content hash is new or changed, in one batch;
- refreshes the structured columns of every document without re-embedding;
- deletes SKUs that are no longer published.

## Benchmark relevance

`eval/retrieval-benchmark.json` (schema version 1) is generated by DemoStore from the clean store:

- `RetrievalRelevanceOracle` reuses `ConstraintEvaluator` over `AuthoritativeFacts(clean)` with the discovery
  projection (downstream constraints removed).
- A SKU is relevant if it is in the requested category, in stock, and violates no discovery constraint. Nothing is
  hand-labelled.
- `hardFilterPoolSize` = clean SKUs passing the hard filters; a case is semantic-discriminating when the pool is larger
  than the relevant set.
- Groups:
  - shopper-derived: one case per shopper intent, using the intent text;
  - discovery-only: templates R01-R10; generation fails if a template leaves semantic retrieval no job.
- Outcomes:
  - `RelevantProductsExist` cases are scored.
  - `NoRelevantProduct` cases are reported separately (empty results and average returned count). Hybrid correctly
    returned empty for 2/2 cases on the observed OpenAI run; SemanticOnly returned 5 candidates for both. Nearest-
    neighbor retrieval alone cannot reliably express “no suitable product”.
  - `InsufficientDiscoveryInformation` cases (derived from shopper intents that need clarification) are excluded from
    retrieval scoring. Clarification belongs to the later shopper reasoning layer, not to candidate generation.

Relevance comes from hidden clean truth while the index is built from published observable data. Scores therefore
measure published-data retrieval readiness plus retrieval strategy, not isolated embedding-model quality. Missing or
misleading published data can lower them legitimately, and retrieval never corrects published data. Retrieval relevance
is not factual correctness: semantic search can surface a misleading description, and truth checking belongs to later
semantic analysis.

## Metrics

Per scored case at K:

- Recall@K = relevant in top K / all relevant.
- Precision@K = relevant in top K / returned (null if nothing is returned).
- Hit@K = at least one relevant SKU in the top K.
- Max achievable recall = min(K, relevant) / relevant.

Aggregates are macro averages per mode for each group: shopper-derived, discovery-only, combined, and the
semantic-discriminating subset (also broken down by shopper-derived vs discovery-only in the README results).
HitRate@K is the share of cases with a hit.

Accepted Milestone 2 discriminating Recall@5 (OpenAI `text-embedding-3-small`, observed run): ShopperDerived
Structured 0.3475 / Semantic 0.6553 / Hybrid 0.7460; DiscoveryOnly 0.3664 / 0.3306 / 0.5239; Combined 0.3574 /
0.4844 / 0.6290. Corresponding Precision@5 and HitRate@5 are recorded in the README. Do not tune the retrieval
algorithm further against these numbers.

Observed per-query regressions (not tuned away): on the same OpenAI run, Hybrid Recall@5 falls below StructuredOnly
on R03 (0.1667 vs 0.3333; laptop bag that stays dry in rain) and R05 (0.3750 vs 0.5000; budget meeting headset).

## Benchmark report provenance

Every `retrieval/benchmark-<model>.json` starts with `provenance`:

- `storeVersion`
- `benchmarkSchemaVersion`
- `embeddingProvider`
- `embeddingModel`
- `embeddingDimensions`
- `k`
- `index`
- `runTimestampUtc`

`runTimestampUtc` is set only for real-provider runs (observed runs) and comes from an injected `TimeProvider`. The
hashing baseline omits it, so it stays byte-identical and reproducible offline.

## Trust boundary

- **Production path.** `published/` goes through the search document builder, the indexer and the index, and comes
  out as search results.
  - It reads only `published/` (`PublishedStore`).
  - It rejects clean stores and unsupported schemas.
  - It never touches `clean/`, ground truth, defect metadata, oracle results or benchmark expectations.
- **Evaluation path.** Search results plus `eval/retrieval-benchmark.json` produce metrics (`Retrieval/Benchmark/`,
  the `benchmark` command only).
- **Enforcement:**
  - reflection over the public retrieval surface;
  - a narrow source scan;
  - behavioral tests with published-only and poisoned `clean/`/`eval/` datasets;
  - Core references no AI or database packages.

## Limitations

- The hashing provider is lexical; its results are a reproducible baseline, not a semantic-quality measurement.
- Numeric thresholds are filters, so embeddings are never asked to compare numbers. Fuzzy needs rely entirely on the
  query text.
- The corpus is small and synthetic; absolute scores do not transfer to real catalogs.
- Retrieval does not verify description claims (MisleadingDescription remains a later concern).
- **SKU variant saturation.** Results are ranked per SKU, so near-duplicate size/color variants of one product can
  occupy several top-K slots. Product-level diversification is deferred beyond Milestone 2.
- **NoRelevantProduct.** Semantic-only nearest-neighbor search always returns K neighbors when the index is non-
  empty; it cannot express “no suitable product”. Hybrid emptiness on those cases comes from hard filters.
- **Per-query Hybrid regressions** on R03 and R05 are accepted observations, not targets for further retrieval tuning.
